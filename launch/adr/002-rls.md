# ADR 002 — Tenant isolation: app filter + Postgres RLS

**Status**: Decided 2026-11-25. Implementation Day 2.

## Context

Every tenant table today ships with explicit `WHERE company_id = %s` in the application layer. One typo leaks another customer's data; such bugs are historically the most common SaaS breach.

## Options

**A — Keep app-only filter.** Fast. Not defense-in-depth.
**B — Add Row-Level Security.** Defense in depth; one line of config (RLS) fails closed when the app forgets the filter.
**C — Separate database per tenant.** Operationally expensive, breaks the current pattern.

## Decision

**Option B.** Keep every current `WHERE company_id = ...` AND add RLS policies on every tenant table. The connection sets `app.company_id` from the auth dep; policies filter on `current_setting('app.company_id')::uuid`. The job runner connects with a super-role that bypasses RLS and sets the row's tenant explicitly.

## Trade-offs

- **Cost**: dev time to add `SET LOCAL app.company_id` at the start of every request transaction (middleware).
- **Benefit**: proven by regression test that revokes app-level filters and asserts 0 cross-tenant rows. See `14-API-TEST-PLAN.md`.
- **Risk**: query planner costs for RLS predicates. Mitigation: all tenant tables already have `company_id` leading index columns.

## Implementation plan

1. Alembic migration that enables RLS on: `companies`, `memberships`, `bots`, `documents`, `document_versions`, `chunks`, `jobs`, `job_attempts`, `publications`, `publication_sources`, `visitor_sessions`, `conversations`, `messages`, `feedback`, `leads`, `lead_forms`, `lead_form_fields`, `usage_daily`, `usage_reservations`, `analytics_events`, `audit_events`, `webhook_endpoints`, `webhook_deliveries`, `crawl_jobs`, `idempotency_keys`, `bot_domains`, `bot_links`. Each gets:
   ```sql
   ALTER TABLE t ENABLE ROW LEVEL SECURITY;
   CREATE POLICY t_tenant ON t
     USING (company_id = current_setting('app.company_id')::uuid);
   CREATE POLICY t_tenant_ins ON t FOR INSERT
     WITH CHECK (company_id = current_setting('app.company_id')::uuid);
   ```
2. FastAPI middleware: after auth resolves `principal.company_id`, run `SET LOCAL app.company_id = ...` in the request transaction.
3. Service-role bypass: worker + migration use a role with `BYPASSRLS`. Only two roles exist: `app_user` (RLS on) and `app_admin` (RLS off, worker only).
4. Regression test: comment out the `WHERE company_id` filter in list routes; assert the API still returns zero cross-tenant rows.

## Rollback

`ALTER TABLE t DISABLE ROW LEVEL SECURITY` reverts instantly. App filters remain and still protect.
